# 🥇 1위. KillScore

> **PR 하나를 받아 그 diff에 버그를 심어보고, 당신의 테스트가 그걸 잡는지 점수로 매겨 머지를 막는 릴리스 게이트.**

| 항목 | 값 |
| --- | --- |
| 조준 상 | Best SaaS Product ($4,000) + NexFellow Product Excellence |
| 경쟁 밀도 | **0건** (05문서 공백 표 1행) |
| 구현 시간 | 7h (코어 4h + SaaS 껍데기 2h + 여유 1h) |
| 외부 데이터 | GitHub API (오늘 200 확인) |

### 왜 이게 1위인가

테스트 커버리지 90%는 거짓말입니다. 코드가 실행됐다는 뜻일 뿐 버그를 잡았다는 뜻이 아닙니다. 2026년 현재 코드의 상당 부분이 생성 도구로 작성되고 테스트도 마찬가지로 생성되면서, **"통과하는데 아무것도 검증하지 않는 테스트"** 가 대량 생산되고 있습니다. 뮤테이션 테스팅은 20년 된 해법이지만 느리고 설정이 복잡해서 아무도 CI에 못 넣었습니다.

KillScore는 **PR의 diff 범위에만** 뮤테이션을 적용합니다. 전체 코드베이스가 아니라 바뀐 20줄에만. 그래서 90초 안에 끝나고, 그래서 CI에 들어갈 수 있습니다.

### 심사위원 정렬 (이 아이디어의 결정적 강점)

- **Lakshmi Vidya Peri** - TMMi America 이사회, 전 Dell 수석엔지니어. TMMi는 **테스트 성숙도 모델** 그 자체입니다. 1:1 정렬.
- Disha Patel(Apple), Ishan Shah(PayPal), Gayathri Chilukala(Microsoft), Nanda Kishore Kande(Visa) - 전부 대기업 프로덕션에서 머지 게이트를 겪은 사람들입니다.
- Pulkit Arya(Pointer) - 코드 리뷰 도구 창업 엔지니어.

**엔지니어 심사위원 8인 전원이 "어제 이걸 겪었다"고 느낄 주제입니다.**

### 최소 기능 (이것만 만듭니다)

1. GitHub PR URL 붙여넣기 → diff 가져오기 (인증 없이 public repo 읽기, 오늘 200 확인)
2. **결정론적 뮤테이션 엔진**: diff 안의 Python/JS 표현식에 6종 변형 적용 (`>` ↔ `>=`, `+` ↔ `-`, `and` ↔ `or`, 상수 ±1, `return x` → `return None`, 조건문 반전). AST 기반, LLM 없이 순수 파이썬
3. 샌드박스에서 테스트 실행 → 각 변형이 죽었는지(kill) 살아남았는지(survive) 판정
4. **KillScore = kill / total**, 임계값 미달이면 빨간 배지
5. **LLM의 역할 (여기가 Innovation 20%)**: 살아남은 변형 각각에 대해 "이 변형이 살아남았다는 것은 무엇이 검증되지 않았다는 뜻인가"를 한 문장으로 설명하고, **그 변형을 죽이는 테스트 케이스를 생성**. 생성된 테스트를 다시 돌려 실제로 죽는지 검증한 뒤에만 제시 (자체 검증 루프)
6. 대시보드: 리포지토리 목록, PR별 점수 히스토리, 임계값 설정, 요금제 페이지

### 영상 핵심 장면 (30초에 끝남)

> 화면 왼쪽: `Coverage 94%` 초록 배지.
> 오른쪽: KillScore가 같은 PR을 돌린다. `KillScore 31% - 13 mutants survived`.
> 살아남은 변형 하나를 클릭. `>= 를 > 로 바꿨는데 테스트가 전부 통과했습니다. 경계값이 검증되지 않았습니다.`
> 옆에 생성된 테스트 3줄. 클릭하면 실행되고 변형이 죽는다. `KillScore 31% → 84%`.
>
> **"커버리지는 94%였습니다. 실제로 잡히는 버그는 3분의 1이었습니다."**

이 한 장면에 Technical(25) · Impact(25) · Innovation(20)이 동시에 들어갑니다.

### 정량 수치 3개 (Impact 25%용, 오늘 직접 측정)

1. 인기 오픈소스 레포 3개에 돌려서 "커버리지 vs KillScore" 격차 실측
2. PR당 소요 시간 (전체 뮤테이션 대비 diff 한정 시 몇 배 빠른가)
3. 생성된 테스트의 실제 kill 성공률

### 리스크와 대응

| 리스크 | 대응 |
| --- | --- |
| 임의의 레포에서 테스트 실행이 실패 (의존성 설치) | **데모용 레포 3개를 미리 준비**하고 그 3개는 컨테이너 이미지를 캐싱. 심사위원이 아무 레포나 넣으면 "지원 언어: Python/JS, 데모 레포로 시작하기" 버튼을 크게 노출 |
| 샌드박스 보안 | 타임아웃 + 네트워크 차단 서브프로세스로 충분. 완전 격리는 오늘 만들지 않음. 아키텍처 슬라이드에 "현재 프로세스 격리, 프로덕션은 gVisor" 로 적으면 feasibility 점수 |
| 뮤테이션 6종이 너무 단순해 보임 | 그게 장점입니다. 결정론적이고 설명 가능합니다. 슬라이드에 "연산자 6종 → 확장 가능한 룰 레지스트리" 로 표기 |

# 🥈 2위. DeadDep

> **당신 레포가 의존하는 라이브러리 중 몇 개가 이미 수명이 끝났는지, 언제 터질지, 무엇부터 고쳐야 하는지 하나의 D-day 보드로.**

| 항목 | 값 |
| --- | --- |
| 조준 상 | Best SaaS Product + NexFellow Innovation |
| 경쟁 밀도 | 낮음 (05문서 "AI 비용/거버넌스" 인접, 1건) |
| 구현 시간 | 5h |
| 외부 데이터 | **오늘 전부 200 확인**: endoflife.date, OSV.dev, PyPI, npm registry |

### 피치

`npm audit`은 취약점만 봅니다. Dependabot은 버전만 봅니다. **아무도 "이 스택이 언제 죽는가"를 날짜로 보여주지 않습니다.** Node 25는 2026-06-01에 이미 EOL이 지났고(오늘 endoflife.date에서 직접 확인), 그 사실을 모르는 레포가 수십만 개입니다.

DeadDep은 `requirements.txt` / `package.json` 하나를 받아 각 의존성의 EOL 날짜, 알려진 취약점, 마지막 릴리스 이후 경과일을 합쳐 **D-day 순으로 정렬된 보드**를 만듭니다.

### 최소 기능

1. 파일 업로드 또는 GitHub 레포 URL
2. 각 패키지를 endoflife.date + OSV.dev + PyPI/npm에 조회 (전부 오늘 검증됨, 키 불필요)
3. **결정론적 위험 점수**: (EOL까지 남은 일수) × (취약점 심각도) × (마지막 릴리스 이후 경과) 가중합
4. D-day 보드: `D-0 이미 만료`, `D-45`, `D-210` 으로 정렬된 카드
5. **LLM의 역할**: 상위 5개에 대해 "이 업그레이드가 왜 어려운가"와 "마이그레이션 첫 3단계"를 레포의 실제 import 패턴을 읽고 작성. 일반론이 아니라 이 코드베이스에 대한 문장
6. 요금제 페이지 + 주간 알림 설정 화면

### 영상 핵심 장면

> 유명 오픈소스 레포의 `package.json` 을 붙여넣는다. 3초 뒤 보드가 뜬다.
> `D-0 · Node 25 · EOL 2026-06-01 · 107일 경과` 가 맨 위에 빨갛게.
> **"이 레포는 오늘 기준 107일째 수명이 끝난 런타임 위에서 돌고 있습니다."**

### 리스크

- 외부 API 4개를 동시에 씁니다. 레이트리밋이 걸릴 수 있으므로 **결과를 SQLite에 캐싱**하고 데모용 레포 2개는 미리 캐시를 채워두십시오. (이게 F3를 만족시키는 유일한 조건)
- Technical 점수가 KillScore보다 낮습니다. 본질이 조회 + 정렬이기 때문입니다. 위험 점수 공식을 슬라이드에 수식으로 노출해 보완하십시오.

# 🥉 3위. SilentSLO

> **LLM이 틀린 답을 자신 있게 반환한 횟수를 에러 버짓으로 관리하는 대시보드. 500 에러는 잡히는데 조용한 실패는 아무도 안 잡습니다.**

| 항목 | 값 |
| --- | --- |
| 조준 상 | Best SaaS Product + NexFellow Innovation |
| 경쟁 밀도 | 🟠 **주의: 에이전트 관측은 극포화 클러스터** (Langfuse, Phoenix, Helicone, Braintrust가 이미 존재) |
| 구현 시간 | 6h |
| 외부 데이터 | 없음 (자체 트래픽) |

### 피치

프록시 한 줄을 끼우면 당신의 LLM 호출이 전부 지나갑니다. 각 응답에 대해 **LLM 없이 판정 가능한 불변식**을 돌립니다. JSON 스키마 위반, 요청하지 않은 필드, 인용한 문서에 없는 숫자, 이전 턴과 모순되는 사실. 이 불변식 위반율이 SLO가 되고, 에러 버짓이 소진되면 알림이 갑니다.

### 최소 기능

1. OpenAI 호환 프록시 엔드포인트 (`base_url` 만 바꾸면 연결)
2. 불변식 6종 (전부 결정론적): JSON 파싱 실패 / 스키마 위반 / 근거 문서에 없는 숫자 / 금칙어 / 빈 응답 / 이전 응답과 수치 모순
3. SLO 대시보드: 위반율 시계열, 에러 버짓 게이지, 위반 샘플 드릴다운
4. **LLM의 역할**: 위반 클러스터를 묶어 "무엇이 깨졌는가" 요약. 판정 자체는 LLM이 하지 않음 (이것이 핵심 차별점)
5. 요금제 + API 키 발급 화면

### 심사위원 정렬

**Vasuki Uday Kiran Vudathala** - ServiceNow Staff Performance Engineer. SLO와 에러 버짓은 이 사람의 모국어입니다. Aakanksha Joshi(IBM AI 아키텍트), Sourav Sarkar(AWS SA)도 정렬.

### 영상 핵심 장면

> 왼쪽 패널: 모든 인프라 지표가 초록. `p99 180ms`, `5xx 0.00%`.
> 오른쪽: SilentSLO. `Silent failure rate 4.2% · error budget 12% remaining`.
> 위반 하나를 클릭. 응답이 인용한 매출 숫자가 원본 문서에 없다.

### 리스크

- 좌측 "인프라 전부 초록" 패널을 목업으로 만들면 주최측이 배제한 `concept videos` 에 근접합니다. **반드시 실제로 돌아가는 패널이어야 합니다.**

# 4위. AgreeGate

> **LLM이 매긴 점수가 사람이 매긴 점수와 얼마나 일치하는지 측정하고, 일치하지 않으면 배포를 막는다.**

| 항목 | 값 |
| --- | --- |
| 조준 상 | NexFellow Product Excellence |
| 경쟁 밀도 | 0건 |
| 구현 시간 | 5h |
| 외부 데이터 | 없음 |

### 피치

2026년의 모든 팀이 "LLM이 LLM을 채점하게" 하고 있습니다. 그런데 그 채점자가 사람과 얼마나 일치하는지 재는 팀은 거의 없습니다. AgreeGate는 샘플 30건을 사람에게 주고, 같은 30건을 LLM 채점자에게 주고, **Cohen's kappa** 를 계산합니다. kappa가 임계값 아래면 그 채점자는 배포되지 않습니다.

### 최소 기능

1. 평가 루브릭 정의 화면
2. 사람 라벨링 UI (키보드만으로 30건을 3분에)
3. LLM 채점자 실행 (3개 프로바이더 비교: Anthropic / OpenAI / Featherless)
4. **kappa 계산 + 불일치 항목 드릴다운** (순수 통계, LLM 없음)
5. 게이트: kappa < 0.6 이면 빨간 배지 + 배포 차단 웹훅
6. 서명된 증적 로그 (append-only 해시체인)

### 영상 핵심 장면

> 세 프로바이더의 kappa가 나란히. `0.71 / 0.58 / 0.34`.
> **"당신이 쓰는 채점자는 세 번 중 한 번 당신과 다르게 판단합니다. 그 점수로 배포를 결정하고 계셨습니다."**

### 리스크

- Impact가 개발자 내부 문제에 한정됩니다. PM 심사위원 7명에게는 덜 와닿습니다.
- 데모에 사람 라벨링 3분이 필요해 영상이 늘어집니다. 미리 라벨링된 데이터셋으로 시작하고 라벨링 UI는 15초만 보여주십시오.

| 외부 데이터 | 없음 (합성 매크로 세트) |

### 피치

지원팀의 매크로/답변 템플릿은 시간이 지나면서 서로 모순됩니다. 환불 정책 매크로는 30일이라 하고, 구독 취소 매크로는 14일이라 합니다. 아무도 200개를 한 번에 읽어본 적이 없습니다. TicketDrift는 매크로들을 주장 단위로 쪼개 **모순 그래프**를 그립니다.

### 최소 기능

1. 매크로/FAQ 업로드 (CSV, Markdown, 또는 URL)
2. LLM으로 각 문서에서 **원자적 주장** 추출 (숫자, 기간, 조건)
3. **결정론적 모순 탐지**: 같은 엔티티에 대한 서로 다른 수치/기간을 규칙으로 검출
4. 모순 그래프 시각화 (노드 = 매크로, 빨간 엣지 = 충돌)
5. 각 충돌에 대해 "어느 쪽이 최신인가" 근거 제시 + 수정 제안
6. 대시보드 + 요금제

### 영상 핵심 장면

> 200개 매크로가 그래프로 펼쳐지고, 빨간 엣지 11개가 켜진다.
> 하나를 클릭: `환불 기간 - 매크로 #42는 30일, 매크로 #178은 14일`.
> **"당신의 지원팀은 같은 질문에 두 가지로 답하고 있습니다. 11곳에서."**

### 리스크

- 합성 데이터라는 점이 드러나면 Impact가 깎입니다. **실제 공개 문서(오픈소스 프로젝트의 FAQ, 공개 SaaS의 헬프센터 문서)를 스크랩해 쓰면** 훨씬 강하지만, 남의 사이트 크롤은 F4 위반입니다. 타협: 공개 GitHub 레포의 `docs/` 를 쓰십시오 (GitHub API 오늘 200 확인).

# 6위. PayloadProof

> **당신의 API 문서와 실제 응답이 어디서 어긋나는지 스펙 대조로 찾아낸다.**

| 항목 | 값 |
| --- | --- |
| 조준 상 | NexFellow Product Excellence |
| 경쟁 밀도 | 🟠 중간 (개발자 도구 클러스터 ~6%) |
| 구현 시간 | 4h (가장 빠름) |
| 외부 데이터 | 없음 |

### 피치

OpenAPI 스펙은 항상 거짓말을 합니다. 문서에는 `nullable: false` 인데 프로덕션은 null을 반환합니다. PayloadProof는 스펙과 실제 응답 샘플을 대조해 **드리프트 목록**을 만들고, 각 드리프트에 대해 누가 고쳐야 하는지(스펙인가 코드인가)를 판정합니다.

### 최소 기능

1. OpenAPI YAML 업로드 + 응답 샘플 업로드 (또는 프록시로 수집)
2. 결정론적 스키마 대조 (타입, nullable, 필수 필드, enum)
3. 드리프트 테이블 + 심각도
4. LLM이 각 드리프트에 대해 "스펙을 고칠 것인가 코드를 고칠 것인가" 판단 근거 작성
5. 요금제

### 영상 핵심 장면

> `47개 엔드포인트 중 19개가 문서와 다릅니다.` 목록이 주르륵.
> **"당신의 API 문서는 19곳에서 거짓말을 하고 있습니다."**

### 리스크

- 구현이 쉬운 만큼 Innovation 20%가 약합니다. 이미 유사 도구가 있습니다.
- **다만 가장 안전한 선택입니다.** 4시간이면 확실히 완성되므로, 02:00 KST에 1~3위가 무너졌을 때의 비상 대안으로 기억해 두십시오.

# 7위. i18nDebt

> **당신 제품의 번역이 원문보다 몇 커밋 뒤쳐져 있는지, 어느 화면이 깨지는지.**

| 항목 | 값 |
| --- | --- |
| 조준 상 | Best SaaS Product |
| 경쟁 밀도 | **0건** (05문서 공백 표) |
| 구현 시간 | 5h |
| 외부 데이터 | GitHub API (오늘 200 확인) |

### 피치

다국어 제품에서 원문 문자열은 매일 바뀌는데 번역은 분기에 한 번 업데이트됩니다. 그 사이 사용자는 영어와 한국어가 섞인 화면을 봅니다. i18nDebt는 레포의 로케일 파일들을 커밋 히스토리와 함께 읽어 **각 언어가 원문 대비 몇 일 뒤쳐졌는지**를 부채로 환산합니다.

### 최소 기능

1. GitHub 레포 URL → `locales/` 디렉터리 탐색
2. 각 키의 원문 마지막 수정 커밋 vs 번역 마지막 수정 커밋 비교 (결정론적)
3. 언어별 부채 점수 + 가장 오래된 미갱신 키 목록
4. LLM이 누락/구식 키에 대해 번역 초안 생성 + 길이 오버플로 경고 (UI 깨짐 예측)
5. 대시보드 + 요금제

### 영상 핵심 장면

> `한국어 번역은 원문보다 평균 94일 뒤쳐져 있습니다. 미번역 키 212개.`
> 실제 화면 미리보기에 영어와 한국어가 섞여 나오는 스크린샷.

### 리스크

- 로케일 파일 구조가 프로젝트마다 제각각입니다. **지원 포맷을 JSON 평면 구조 하나로 못 박고** 데모 레포 2개를 미리 정해두십시오.
- 심사위원 중 이 고통을 겪은 사람이 적습니다. 한국 개발자에게는 자명하지만 미국 심사진에게는 설명이 필요합니다.
